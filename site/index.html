It reads what just scrolled past.

Shell history only knows what you have typed before. wisp also reads the last 60 lines of your terminal, the files in the directory and your git branches. The pod that is crash-looping, the compose file you just listed, the PID holding port 3000: each of those names is one → away. 

$ kubectl get pods -n billing
NAME                        READY   STATUS             RESTARTS
api-7d9f8b6c4-x2kqp         0/1     CrashLoopBackOff   12
worker-5c8d7f9b6-mn4lz      1/1     Running            0

$ kubectl logs -n billing api-7d9f8b6c4-x2kqp

Completions are what Qwen2.5-Coder produced in wisp’s test scenarios. The terminal output around them is a test fixture.

Does it work in your terminal?

wisp works in any terminal emulator on macOS and Linux. To read the screen it needs one of these four sources.

tmux

Any terminal emulator: Ghostty, iTerm2, Alacritty, Terminal.app and others. If your shell runs inside tmux, wisp reads the pane. There is nothing to configure.

tmux capture-pane -p -J -t <pane> -S -60
WezTerm

wisp asks WezTerm for the text of the current pane. There is nothing to configure.

wezterm cli get-text --pane-id <pane> --start-line -60
kitty experimental

Needs allow_remote_control and listen_on in kitty.conf. This source follows kitty’s remote-control documentation and has not been verified on a real kitty install.

kitty @ get-text --match id:<window> --extent screen
Anything else

Set WISP_SCREEN_CMD to a command that prints your screen as plain text. It takes priority over the other three.

export WISP_SCREEN_CMD='your-terminal dump-screen'

With no screen source, for example a bare Ghostty or Terminal.app window outside tmux, wisp still completes from your shell history, the files in the current directory, your git branches and the commands you ran this session with their exit codes. wisp doctor names the source it found for the current shell.

How it works

A zsh plugin talks to a small daemon over a Unix socket. The daemon builds a prompt from your screen, history, directory and branches, then asks llama-server on 127.0.0.1 to continue the line.

How it works, in the docs

  • After a command wisp predicts the next one while the prompt is still empty.
  • While you type it completes the line after a 60 ms pause, and keeps the suggestion for as long as you type along with it.
  • Mid-word the half-typed word goes through a grammar, so the model has to continue feat/p and cannot start a different word. This is token healing. It took the 3B model from 3/8 to 7/8 in the eval below.
  • To accept press →, End or Ctrl F. Alt F takes one word. If zsh-autosuggestions is loaded, wisp suggests through it and your keys stay as they are.

The eval is eight scenarios where the right answer appears only in terminal output: a compose file, a git branch, a failing test, a pod name, a stack-trace path, a PID, the next command after git add, and a container name. Run wisp complete and wisp status to measure your own.

Nothing you type leaves your machine.

The model is Qwen2.5-Coder, served by llama.cpp on 127.0.0.1:8012 and kept running by launchd on macOS or a systemd user unit on Linux. Your screen, history and keystrokes go to that process and nowhere else. There is no account and no API key.

The network is used during install only: install.sh fetches the binary from GitHub, and llama.cpp fetches the model weights from Hugging Face. After that wisp works offline.

wisp pause stops suggestions until you run wisp resume. wisp status shows the loaded model, the latency and recent suggestions. On macOS, wisp setup --menubar puts the same readout in the menu bar.

Know the limits before you install.

  • zsh only. bash and fish are not supported.
  • Screen reading needs a source. That means tmux, WezTerm, kitty or your own command. Without one, suggestions come from history, files and git, and a name that only appeared in output is out of reach.
  • kitty is experimental. Nobody has verified it on a real kitty install yet. Reports are welcome.
  • The model takes RAM. Budget roughly 2 to 4.5 GB while it is loaded. We measured about 4.3 GB for 3B. The low end is an estimate from the 1.65 GB file of the 1.5B model.
  • The menu bar item is macOS only. On Linux, wisp status prints the same information.
  • It is wrong sometimes. The best score on our own eight scenarios is 7/8, and eight scenarios is a small eval. A wrong suggestion stays grey until you accept it.
  • One machine measured. Every number on this page comes from an Apple M5. We have no figures for Linux or Intel Macs.

Install

You need macOS or Linux, zsh, and llama.cpp. zsh-autosuggestions is optional.

  1. Install llama.cpp. On Linux without Homebrew, take a llama.cpp release binary and put llama-server on your PATH.

    brew install llama.cpp

  2. Install wisp. The script puts a prebuilt binary for your OS and CPU in ~/.local/bin. You can read install.sh first.

    curl -fsSL https://raw.githubusercontent.com/lolabradora/wisp/main/install.sh | sh

    Or build it yourself with a Rust toolchain.

    cargo install --git https://github.com/lolabradora/wisp

  3. Download the model (1.65 GB, once) and start the background service that keeps llama-server running. wisp setup --model 3b picks the larger model.

    wisp setup

  4. Load the plugin, then open a new shell. If you use zsh-autosuggestions, put this line after it.

    echo 'eval "$(wisp init zsh)"' >> ~/.zshrc

Is it working?

wisp doctor checks llama-server, the model, the daemon, your ~/.zshrc and the screen source for this shell. Each failed check comes with a fix hint. To remove wisp’s background services later, run wisp uninstall.

wisp doctor
